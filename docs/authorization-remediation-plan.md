## Scope and baseline decisions

This branch already contains the platform tenant/plan/subscription control plane (V40–V44), platform-only grant storage, tenant lifecycle model, platform audit, platform support-grant registry, platform React workspace, and relevant tests. These implementations will be extended, not replaced.

The product/SRS boundary defines one POS branch and one designated stock location per vendor as Commercial MVP. Additional branches, warehouses and transfers are later Operations scope. The missing explicit employee-to-register assignment is in MVP scope. A separate warehouse-assignment table is **DEFERRED** until multiple warehouses exist; in MVP the designated stock location is the assigned branch stock location.

The SRS ownership matrix is sufficiently decisive for POS visibility: cashier transaction/session views are own-cashier/own-session; branch-wide transaction/session visibility is supervisor/manager reporting access. This plan uses `POS_REPORT_VIEW` as the existing explicit branch-report permission where a branch-wide report is intended, while cashier detail and drawer data remain owner-filtered. This is not a blanket grant of branch transaction access.

No MFA implementation may relax the existing production platform-login denial until a verified MFA enrollment/challenge flow is complete. A password-only platform token is never an acceptable fallback.

## Implementation order

1. **P0 platform authentication/permission boundary and vendor role/employee administration**. Do not relax the current production MFA fail-closed gate.
2. **P0 reusable service authorization guard and canonical endpoint/route registry**, then systematically apply to current service entry points.
3. **P0/H1 tenant isolation and role × endpoint tests** for all implemented routes/services.
4. **P1 register assignments, shift-history/UI permission parity, register OPEN/CLOSING DB uniqueness**, then tenant entitlement enforcement.
5. **P2 architecture and browser hardening**. Playwright is not currently an installed dependency; only add it if repository CI/runtime can execute it without weakening the existing pipeline.

## Delivery controls

- Target only `feature/platform-super-admin-v2`; use expected-head compare-and-swap when updating the ref.
- Additive Flyway migrations only; never edit V1–V44.
- Preserve production platform-login fail-closed behavior until MFA is completely operational.
- No UI placeholders. All new visible controls must call permission-protected APIs and persist audited state.
- Do not claim multi-warehouse, CRM, lead, quotation, fulfilment, installation or service authorization is implemented by this work; those domains remain deferred until their vertical slices exist.
- CI/test results must be tied to the resulting branch commit and exact workflow run.
